# 0020. The ECS: archetype chunks, access-derived scheduling, 64-bit transforms

- **Date:** 2026-10-15
- **Status:** Accepted

## Context

CLAUDE.md §8.7 asks for an archetype-based ECS with structure-of-arrays
storage in 16 KiB chunks and generational 32-bit entity IDs; systems that
declare their reads and writes, scheduled from a dependency graph and run
in parallel as jobs; components defined with X-macros that generate the
struct, its field metadata, and serialization; a transform hierarchy
updated in parallel by depth; scene serialization; prefabs with
overrides; and an event stream for the editor. Phase 8 ends when
million-entity benchmarks are recorded and scenes round-trip (§12).

Constraints from the rest of the plan:

- No global mutable state outside an engine context (§2). The registry
  cannot be a process-wide table filled by static constructors.
- No hidden allocation (§1.4) and none per frame in steady state (§10.5).
- Deterministic simulation for identical inputs (§2), for any worker
  count.
- 64-bit world positions on the CPU, camera-relative 32-bit on the GPU
  (§8.2).
- Per-frame CPU work as jobs (§2), with the frame's CPU budget in §10.5.
- The `scene` module sits at the same rank as `asset` (§4), so it builds
  on `core`, `math`, `platform`, and `jobs` only.

## Decision

1. **Archetype storage in 16 KiB SoA chunks.** Each distinct component set
   is an archetype. Its chunks hold a header, one change version per
   column, the entity handles, and one packed column per component with
   data, each on a cache line. The capacity is computed per archetype.
   Removal swaps the archetype's last entity into the hole, so every
   chunk but the last is full and iteration never skips holes. Tags
   (zero-size components) are mask bits without columns. Chunks come from
   1 MiB slabs the world allocates on demand and keeps for reuse
   (`nph_world_trim` returns empty slabs).
2. **Entities are generational handles from the core handle pool**
   (ADR-0006), with the index width chosen from the world's capacity (at
   least 10 bits) and FIFO reuse after 1024 releases. A per-slot record
   points at the entity's chunk and row. The capacity is fixed at
   creation, so the entity table never reallocates.
3. **A registry per world, ids by registration order.** The five
   built-ins (Name, LocalTransform, WorldTransform, Hierarchy,
   PrefabInstance) are registered first with constant ids. Another world
   can copy a registry (`registry_from`), which prefabs and the editor's
   play-in-editor snapshot need. Components are capped at 256, so an
   archetype's signature is a 32-byte mask and query matching is a few
   word operations.
4. **Reflection by X-macro, descriptor functions instead of globals.**
   `NPH_COMPONENT_STRUCT` generates the struct. `NPH_COMPONENT_DEFINE`
   generates a function returning a constant-initialised descriptor (field
   names, kinds, offsets, sizes, editor hints, defaults). The kinds are a
   closed set chosen for serialization (scalars, vectors, quaternions,
   64-bit vectors, entity references, string IDs, inline text). There are
   no pointer fields: references are entities (remapped on load and
   instantiation) or IDs.
5. **Structural changes are single-threaded and frozen during stages.**
   Jobs record them in command buffers. Spawned entities get pending
   handles, which are resolved when the buffer is applied, including
   inside ENTITY fields. Applying creates every spawned entity first,
   directly in its final archetype, then runs the other commands in
   order. Commands on entities that died meanwhile are skipped and
   counted.
6. **Change detection per chunk column, with 32-bit ticks.** Each system
   run gets a fresh world tick. Writes through write queries and the
   write functions stamp the column version. Change filters skip chunks
   whose filtered columns are no newer than a system's previous tick. The
   comparison wraps, and the schedule clamps versions and ticks older
   than 2^30 so it never flips.
7. **The scheduler derives a DAG from declared access.** Systems are
   ordered by `after`/`before` constraints (Kahn's algorithm, ties by
   registration order). Main-thread and exclusive systems split the order
   into stages. Within a stage, a system depends on every earlier system
   it conflicts with (write/write or read/write on a component). Execution
   launches the systems without dependencies. Each finishing system
   launches the dependents it was the last dependency of, so a system
   starts the moment it can, not at a phase boundary. `run_chunk` systems
   are split across jobs by `nph_job_parallel_for`.
8. **Command buffers apply in a worker-count-independent order**: by
   system position, then by the first chunk of the piece that recorded
   them. The pieces of a parallel-for depend only on the chunk count and
   the batch size, so one worker, eight, and a serial schedule produce the
   same world, bit for bit (tested with world hashes).
9. **Transforms: f64 translation, f32 linear part, an intrusive
   hierarchy.** LocalTransform holds a 64-bit translation, a rotation, and
   a scale. WorldTransform holds the composed 3×3 linear part and a 64-bit
   translation, 64 bytes, one cache line. The hierarchy component stores
   parent, first and last child, siblings, and depth, maintained only by
   `nph_world_set_parent` (it is INTERNAL). The transform system updates
   roots per chunk in parallel. It then buckets children by depth with a
   two-pass parallel counting sort and updates each level in parallel. A
   child is recomputed when its own chunk changed or its parent was
   recomputed in the same run.
10. **The event stream is a fixed-capacity array, off by default**:
    spawns, despawns, adds, removes, writes through the API, and
    reparenting, with drops counted when it is full.

## Alternatives considered

- **Sparse-set storage** (EnTT): one packed array per component and
  fast add/remove. But iterating several components needs indirection or
  grouping, and §8.7 specifies archetypes. Moves between archetypes
  (131 ns per add and remove pair in the benchmarks) are the price; the
  editor and gameplay add and remove components rarely compared to how
  often systems iterate.
- **A global component registry** filled by static initialisers. It is
  simple, but it is global mutable state and makes ids depend on link
  order.
- **Per-entity change flags or dirty lists.** They are precise, but cost a
  write per entity per change and a list to maintain. Chunk-column
  versions cost one atomic store per chunk visited. The transform system
  shows the gap: 0.07 ns per entity for a static million.
- **Phase-based scheduling with sync points** (a fixed list of stages that
  all run to completion). It is simpler, but a long system at the end of a
  stage idles every other worker.
- **f32 world transforms with origin rebasing.** That couples every
  system to a shifting origin. §8.2 chose 64-bit positions; a 64-byte
  WorldTransform keeps them at a cost of 8 bytes over an f32 affine.
- **Children lists as a dynamic array component.** That is variable-size
  data in a POD world. Intrusive sibling links keep Hierarchy at 24 bytes
  and make reparenting O(1) plus the subtree's depth update.

## Consequences

- Systems never see a structural change mid-stage; spawning from a job
  means a command buffer, and the entity appears at the end of the stage.
- Determinism holds for any worker count, which the physics phase relies
  on.
- Change detection is per chunk column: a write to one entity marks the
  whole column of its chunk (about 100 entities), so consumers recompute
  that chunk. It is coarse but cheap; finer tracking can be added per
  system if a profile asks for it.
- A dynamic million-entity transform update is bound by memory bandwidth
  (8.5 ns per entity on the reference machine: 56 bytes read and 64
  written per entity). Static content is nearly free. Phase 10's
  GPU-driven renderer will consume WorldTransform columns directly.
- The 256-component and 128-column limits, and 2 KiB per component, are
  hard limits enforced at registration and archetype creation. Raising
  them is a mask-width change.
- Serialization and prefabs build on the descriptors; their format
  decisions are in [ADR-0021](0021-scene-serialization.md).
